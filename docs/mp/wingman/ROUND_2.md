# R2：原僚机、输入、选机与视图

2026-10-31；本地 Ghidra 12.2 / JDK 25.0.5；目标 SHA-256 与 R1 相同。地址均为 RVA。

## 本轮证据和修正

`0CBCC0` 的两段绑定循环不能混为一谈：玩家 i 绑定 group[i]/actor[0]；随后
`W+A82F0` 个辅助上下文（基址 `W+A82F8`、步长 `108`）绑定 group[0]/actor[j+1]。
第二段写 `Actor+1C0=helper[j]`、`Actor+360=helper[j]+18` 所存的 ObjPlane 指针，
还写入模型和定义资源。这个初始化路径支持“原剧情僚机是 group0 的后续 Actor”的判断；
仍须逐任务验证角色身份，不能直接宣称所有任务的 actor1 都是可接管的 Pixy/PJ。

`16EB20` 调 `0C6A50` 时 helper_count=1，玩家数由一个任务编号范围条件决定，
并非无条件 1；编号来自两个存档工作区之一的高 32 位，判式为 `id-0x20 < 10`。
其含义尚未证明，不能把它当成隐藏战役合作开关。`16F6C0` 明确用 count=2、helper_count=0。

修正 R1 的 AI 猜测：`0AC780` 处理辅助模型部件等更新，不是独立的僚机飞行 AI 总入口。
`12F340` 才包含多段从 actor1 开始的编队、目标选择及辅助机体操纵逻辑。
其中还有跨 Unit 查询与武器/目标状态写入，因此把整个 `132240` 跳过会丢失任务和机体更新，
临时缩减 Unit 的 actor_count 也不能作为已证明安全的独占控制办法。

## 人类控制还有 actor0 硬编码

`115C20` 在类别 0/2 下，仅当 `Actor+235==0` 才进入从 `Actor+1B8` 指向的 PlayerContext
复制 pose/目标的路径。这不是“只要人类指针非空就自动接管”。关键比较位置：

| RVA | 消费条件 | 对实现的影响 |
| --- | --- | --- |
| 115D66 | actor index 非零时处理原有模型状态 | 接管后不能只更改后面的 pose 分支 |
| 115EF3 / 115EFA | 非零跳到非玩家路径 | 指针绑定不足以启用 actor1 人类 pose |
| 115FE4 / 116029 | 非零进入 helper/model 消费 | 必须审计与玩家路径互斥关系 |
| 11648E / 116495 | actor0 专用后处理 | 接管后的边界/飞行后处理仍需适配 |

`Actor+234/+235` 同时是目标和弹药所有者使用的 group/actor 身份。
**不允许临时把 +235 改为 0 来骗过判断**：这会制造与 P1 重复的原生身份。
候选办法是对经证明的控制分支作局部适配，保留身份、物理、命中和脚本引用；
实际调用 ABI 和全部写者尚未闭合，当前不能启用这类补丁。

## 第二玩家资源与视图

`0C6A50` 按 count 分配 `27A0` 的玩家块、`70` 的辅助块、两组指针数组和 `3A0` 的视图相关块。
`0C4660` 清理/构造玩家字段；`0C70E0` 加载后续资源；`0CBCC0` 建立很多资源和世界子对象引用；
`0CD880` 才把 selectors、多个目标镜像字段和内嵌摄像机初始化到对应机体。
复制 P1 的 `27A0` 字节或者只把 `W+A87E4` 改为 2 都不满足这些寿命条件。

`0CE880` 通常给每个 P 建立两组相机指针 `P+10B0`、`P+1270`，经 `1FBEC0` 更新后放入
`W+671F0[] / W+67210[]`；`W+67234[]` 存视图的玩家索引，`W+67230` 是至多 4 的视图数。
另有事件相机、回放/特殊视角路径，不应每帧强制覆盖成两台飞行相机。
`0D1780` 每帧先清视图数；在它之前采样会读到上一帧，清空之后过早采样又可能是 0。
本轮实现的取证必须增加**更新后**记录，不能把原先 pre_update 当作本帧最终视图。

`0D2580` 消费这些相机、玩家 HUD 和 viewport 分割状态。把两台 D3D 摄像机画到屏幕只是最外层，
没有第二玩家的原生 HUD/武器/相机资源，不能算复用 VS 分屏完成。

## VS 选择的复用边界

`CModeAircraftSelectVS1/VS2` 共用 166EE0/166F80/167080/167B00；vtable+30 分别返回 0/1
（06A960/11B0D0），是选择页索引，不能当成完成回调。`178FC0` 是 UI 对象构造，
`1F8180` 是 UI 时间/脚本更新，不是选机提交函数。

已经沿全程序数据引用找到选机结果工作区的实际读写者。`16F6C0` 从 active profile 的
`+24C/+250` 取两机编号，`+254/+258` 取两套配装，`+25C/+260` 取附加选项，
颜色从 `+1E0 + aircraft*3` 读取。active profile 由 `31CF18` 决定，基址为 `310EC0/316E78`。
R3 应追踪 `16D1C0/171680/18C6C0/1BD460` 等写者，区分 campaign wingman 字段和 VS 第二玩家字段，
并确认 mode 栈的返回、取消和资源释放；不能把一个全局写入地址当成完整 UI 接口。

## 对 R3 的回写

新增目标：115C20 的 actor0 硬编码与 119A30 非玩家更新、12F340 所有 follower 循环、
上述 selection 工作区读写者、CD880 的 selector 镜像及 leave/reset 资源释放。

原生第二上下文生命周期、AI 独占控制和关键事件分类仍是未通过的功能门槛。
