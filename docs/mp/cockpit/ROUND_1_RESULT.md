# R1 结果：视图与玩家可分离，但显示列表只证明两视图

本地 Ghidra 实际导出 r1（16 函数）和 r1b（9 函数）；原目标 SHA 与总计划一致。
以下均为本轮静态证据；没有新增游戏实测。

## 已闭合的结构事实（S）

1. **视图和玩家分别计数。** 0D2580 用 `W+67230` 遍历视图，从 `671F0/67210` 取两组相机，
   用 `67234[view]` 取 owner，再访问 `W+A8248 + owner*27A0`。正常 HUD 入口 108620 在此调用。
   owner=0 可以索引现有 P0；这是设计两视图共享同一玩家的数据依据，不是运行成功证据。
2. **双玩家额外逻辑有单独条件。** `player_count==2` 才调用另一个玩家的 108620 分支；
   保持 count=1 有机会避开该段 VS 对手/HUD消费，但整个调用图仍需 R3 复核。
3. **四个相机数组槽不等于四套完整绘制能力。** CE880 限制列表 <4，
   0D2580 却使用固定组号 `[1,2,3,4]`，每视图取 `[view]` 和 `[view+2]`。
   201840 总共分配 `5*30 = F0` 的显示列表组，201A40 连接这些组。
   当前仅有两完整视图的明确映射，不扩大为四视图。
4. **场景槽容量独立。** 新追到 0C80E0：`W+A8828` 由任务定义中的条件产生 1/2，
   分别分配 `67130=count*5000`、`67138=count*D10`、`67178=count*28` 等。
   0D2580 用 `W+A8829` 选择这些槽。它们不能仅凭名字当成“每玩家”或“每相机”分配，
   也尚不能称作 GPU 帧缓冲轮换；两个视图能否共享一套场景缓存需审计实际写者。
5. **相机是可独立初始化的数据块候选。** 16E0B0 分配/清零 1C0 字节后调用 004E80。
   004E80 写初始矩阵、尺寸、投影参数和 flags，无分配调用；1FBEC0 更新矩阵。
   1FC350 把矩形、打包的 render-buffer 字段等写成 legacy 命令包，返回 packet+ C0。
   相机对象不是仅有 pose 的两个矩阵。

## 必须保留的限制（O/H）

- 0D2580 同时产生场景/HUD/效果命令并写共享 scratch；不能对一个世界连续调用整段更新两次造视角。
- 20E000/20E490 维护 render-target 状态栈，20EA20 调整资源/采样状态；不能把它们简化为 viewport 开关。
- 自定义第二相机应独立分配，不能复制一个含未知字段的 P 块；调用/释放时点在 R5 继续闭合。
- owner=0 的两次 HUD消费可能修改同一 P 的表现状态；是否可直接重画留给 R3，不提前放行。

## 对 R2 的回写

新增 004E80、005090、005380、202C00、202C90、1FC350 和 106F30/107320 等姿态生产者。
重点恢复 Camera 的尺寸/裁剪/矩阵字节偏移，区分相机旋转、机体姿态及 CameraMode。
场景缓存与命令组的共享风险回写 R5；不再把 W+67130/67138 解释为与玩家数同步增长的资源。
