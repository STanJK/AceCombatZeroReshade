# 《皇牌空战 ZERO》双人在线战役合作补丁实行书

本文件面向实际开发与验收。英文技术规范见
[COOP_PATCH_IMPLEMENTATION.md](COOP_PATCH_IMPLEMENTATION.md)，
逐项逆向契约见 [REVERSE_ENGINEERING_PLAN.md](REVERSE_ENGINEERING_PLAN.md)，
原始依据见 [逆向档案](../reverse-engineering/coop/README.md)。

**交付边界：这是研究和实施方案，尚不是可玩的联机补丁。** 本轮在 Linux
环境中实际运行了 Ghidra CLI，分析用户提供的 EXE；没有运行 Windows 游戏、
双客户端联机或战役通关。静态指令、语义推断、设计方案、未验证契约分别标注，
不把反编译成功等同于函数可安全调用。

## 一、明确要做成什么

两位玩家各运行一个 Windows 游戏实例，进入同一场战役任务，各驾驶一架飞机，
共同完成目标、结算、重试并继续战役，最终完成所有实际战役路线。
主机拥有世界模拟、任务进度和存档；客机拥有自己的输入和本地视角。
保留故事僚机、护航目标和 Boss 的原生脚本身份，客机默认作为新增友军飞行员。

首版固定两个人，只在大厅或任务间加入，不支持中途加入、主机迁移。
主机选择任务、难度和配装，双方确认内容一致后开始。暂停由主机协调，两端一起停；
网络心跳继续。单人被击落后观察队友，两人均被击落才触发团队失败，但任务脚本中
关于主角、护航和特殊失败条件的假设必须逐项审计。断线超时后受控退出到大厅。
主机保存战役进度，客机作为协助者，默认不写自己的战役进度。

## 二、现有代码给出的基础与限制

| 已得到的静态结果 | 对实施的意义 |
| --- | --- |
| 两路原始输入、设备选择、动作映射、按下边沿处理 | 有明确输入接入窗口，但仍需验证设备存在标志和玩家槽绑定 |
| 玩家上下文按人数分配，每个 `0x27A0` 字节 | 原生具有多人基础，不能据此认定战役已经支持 P2 |
| Actor 每项 `0x520` 字节，玩家与任务分组相连 | 原生多处假设玩家 i 对应分组 i 的第一个 Actor |
| 战役 18 步初始化、VS 15 步初始化，共用任务驱动 | 可复用公共机制，不能把 VS 模式整段移植到战役 |
| 血量、伤害归属、死亡副作用、目标选择路径 | 可以建立战斗事件适配层，不能只同步坐标和 HP |
| 选择性历史捕获、姿态插值和事件回放读取路径 | 可参考事件分类；记录含本机资源指针，并非现成网络协议 |
| 三类武器发射入口及部分池结构 | 发射有了具体追踪起点，命中、消失、复用仍需闭环 |
| 线程相关的随机状态及广泛调用点 | 不能用“相同种子”证明两端模拟一致 |

本轮最终索引包含 4,792 个函数，选取 255 个函数导出伪代码、指令和引用信息，
其中 90 个入口形成重点契约记录。其余是支持语料，语义仍有开放项。
这些数量不是“游戏已逆向百分比”。没有证据足以宣称所有合作所需函数都已找全。

最重要的先决条件是：**先在单进程战役中完成双人独立控制，再接网络。**
把人数直接改成 2 可能把任务分组 1 的脚本角色绑定为玩家，破坏敌我、剧情和结算。

## 三、补丁结构与线程规则

| 模块 | 负责内容 |
| --- | --- |
| `coop-core` | 会话、任务世代、Tick、稳定实体 ID、输入序列、事件去重、状态机 |
| `coop-transport` | 首先完成经过认证的直连传输，再接 Internet 匹配、穿透或中继 |
| `coop-runtime` | Windows x64 加载、EXE 哈希校验、钩子安装卸载和故障诊断 |
| `coop-game` | 玩家、实体、飞行、武器、伤害、任务与结算的原生适配层 |
| `coop-view` | 本地玩家全屏视角、HUD、观察模式和状态提示 |
| `coop-trace` | 有界追踪缓冲、双方日志、回放与故障注入结果 |

可保持仓库现有的 Rust 方向，必要处使用小型 C++/汇编 ABI 适配器。
现有 ReShade 桥接继续承担渲染观察职责；旧 XInput 校准代理只有部分导出，
不应直接扩成联机运行时。

网络线程只解析、校验并入队。只有已确认的模拟线程可以解析游戏对象指针、
修改原生状态或调用原生函数。渲染回调只读取不可变遥测。
所有适配器先观察、再验证、最后启用；构建不匹配时不安装游戏地址钩子。
候选入口的 32 字节指纹只是版本证据，不能当作可覆盖的指令长度。

## 四、本地战役第二玩家的施工顺序

1. 从实际游戏安装读取普通战役与 VS 的任务定义、飞机、武器和关联资源。
2. 在 `135B50` 计算分组空间之前，构建生命周期明确的扩展定义。
   优先追加客机友军并建立显式玩家到 Actor 的映射，避免改动脚本引用的旧编号。
3. 为 `0C6A50` 准备两人的完整配装数据。其 ABI 有十个位置，包含一个未使用的
   第七位置；不能依据初次反编译显示的六参数签名写钩子。
4. 按原生顺序分配玩家、辅助数组、分组与 Actor，完成资源和世界连接。
5. 审计所有玩家 i→分组 i 的消费者，包括初始化、常规更新、回放、雷达、
   目标选择、碰撞、伤害归属和表现。只改一个绑定点不够。
6. 验证敌我类别及其所有消费者；两名人类均为战役友军，剧情角色身份保留。
7. 主机跟随 P1、客机跟随 P2，各自全屏。避免为获得第二视口而切到 VS 任务规则。
8. 验证飞行、开火、受伤、任务成功、重试、退出和重新加载。清理正确后才接网络。

任务资源未随 EXE 提供，因此扩展定义格式、资源加载和脚本编号依赖是明确阻塞项。
本节是施工要求，尚不是可直接写入 EXE 的已验证修改序列。

## 五、主机权威与状态复制

主机接受两人的输入，每个有效模拟 Tick 各使用一次，然后执行原生模拟，
收集实体、武器、伤害、任务和结算结果，生成一致快照与有序事件。
客机发送自己的输入，接收主机结果，插值远端对象；自己的飞行预测要等积分器依赖
验证后再启用。客机不能独立提交 AI 伤害、任务目标、分数和战役存档。

不能同时让客机执行原生递归伤害，又应用主机已解析的同一伤害链。
事件必须具备唯一 ID、任务世代和幂等应用范围，避免重复伤害、重复得分、
重复特效和重复导出。主机保留原生接受判定和副作用。

每个序列化字段都要记录：所有写入者、所有消费者、更新阶段、单位、范围、
精度、无指针表示及修正后是否会被另一份状态覆盖。只覆盖位置字段不算完成飞行同步。

## 六、协议草案与预算

以下全是新补丁设计，并非游戏原有结构。按小端显式编码，禁止把接收字节直接
解释为原生结构。公共应用头为 40 字节：

| 字段 | 字节数 |
| --- | --- |
| `ACZ2` 标记、协议版本、消息类型 | 4 + 2 + 2 |
| 随机会话 ID | 16 |
| 任务世代、包序号、Tick | 4 + 4 + 4 |
| 载荷长度、已定义标志 | 2 + 2 |

控制样本为四个 `int16` 轴、`uint16` 按钮和两个 `uint8` 扳机，共 12 字节。
再加输入序列、所属槽和标志后，基础输入载荷为 18 字节。
按下边沿来自连续被接受的按住状态，重复收包不能再次生成按下。

实体网络 ID 使用 `(epoch:uint32, spawn_serial:uint32)`，本地映射到原生槽和生成代。
协议只传合法内容/定义 ID，不传进程指针、虚表、函数地址或任意写入请求。
回放事件里的资源指针必须转换为本地可解析、双方一致的内容标识。

握手、实体创建销毁、战斗结果、任务和结算事件走可靠有序或幂等通道；
输入走有序列的低延迟通道，可带有限近期冗余；快照必须确认基线，缺基线时请求关键帧。
分块快照收到完整组之后才应用，不把缺失 Delta 当作绝对状态。

起始调参目标为输入 60 Hz、快照 20 Hz、插值 100 ms，全部服从原生 Tick 实测。
示例：每项 52 字节姿态，200 个对象、20 Hz，载荷约 208,000 字节/秒，
即 1.66 Mbit/s，尚未包含头部、可靠事件和传输开销。
先用 1,200 字节应用报文预算；20 项姿态加 16 字节快照前缀和公共头共 1,096 字节。
对象数量、姿态格式和性能均未实测，不将示例预算当作性能承诺。

## 七、任务状态机与存档事务

状态依次为大厅、准备、双方就绪、运行、暂停、结算；下一任务或重试产生新世代。
断线或状态缺口进入恢复，失败则回大厅。旧世代所有队列、实体映射和事件失效，
必须在原生内存释放前完成隔离，迟到报文不能解析旧指针。

任务、影片、结算切换由主机提出，客机确认内容与加载完成后，主机统一提交。
客机本地菜单不能独立推进任务或触发保存。网络超时按单调墙钟计时，
模拟 Tick 只在已验证的模拟边界推进，不能使用 Present 次数代替。

战役存档写入前保留主机原始存档；每个任务世代只提交一次结果和解锁。
测试断线发生在加载、成功判定和保存过程时的恢复。客机保持非拥有者策略，
直到结果与写盘边界全部确认。

## 八、必须闭环的逆向契约

RE01–RE18 的详细根地址、状态和实验在
[契约矩阵](REVERSE_ENGINEERING_PLAN.md#2-required-contract-matrix)中维护。
这些项包括构建身份、世界生命周期、Tick、输入、玩家资源、任务定义、
实体创建释放与复用、积分器、武器、伤害、敌我、任务 VM、随机数与时间、
视角、历史恢复、切换、结算存档以及传输。

一个函数只有在取得以下证据后才可进入生产适配层：同构建地址与边界、
完整 Windows x64 参数与返回 ABI、每个指针的所有权和分配器契约、
线程及重入规则、全部相关副作用、一次正常实验和一次失败/清理实验。
仍未闭环的项保留为阻塞门槛，不以推测的函数名代替。

## 九、开发里程碑与验收

| 阶段 | 实际产物 | 放行标准 |
| --- | --- | --- |
| M0 | 只读追踪 DLL、加载器和构建清单 | 进入、暂停、回放、结算、重试、离开均能识别线程、世界和世代，无状态写入 |
| M1 | 本地战役双人构造与独立输入 | 两人均可飞、打、受伤；友军及脚本正确；任务成功、重试和清理通过 |
| M2 | 与游戏无关的协议核心和传输测试 | 丢包、乱序、重复、版本、世代、越界、错误槽和转换幂等测试通过 |
| M3 | 双进程局域网权威模拟 | 飞行、AI、实体状态一致；客机视角正确；一个任务全过程无未解释分歧 |
| M4 | 全武器、任务、切换与结算适配 | 生命周期与战斗事件闭环，无重复伤害、得分或保存，特殊任务通过 |
| M5 | Internet 连接、穿透/中继和诊断 | 真实远程双机完成实测；抖动、断线和恢复行为可解释 |
| M6 | 战役路线覆盖与通关证据 | 从实际数据枚举的所有路线、Boss 和关键状态均覆盖，最终结果与主机存档一致 |

M0、M1 是最大不确定性来源，完成前不承诺工期。
静态地址不能让 M0 自动通过，一关演示不能让 M6 自动通过。

## 十、测试内容与交付物

至少覆盖空中开场、地面目标、护航与剧情任务、Boss、多目标及所有可选择特殊武器、
友军关系、同时击杀、补给修理、单人死亡、双人失败、暂停、失焦、重试、返回和最终结算。
路线清单从实际任务数据取得，不能以任务名称或一次普通通关替代。

建议故障矩阵：RTT 0/50/100/150 ms，抖动 0/20/40 ms，丢包 0/1/3%，
重复与乱序突发、500 ms 输入中断，以及加载和保存时断线。以上是测试点，尚非已达到的容忍度。
保存双方事件序列、状态摘要、误差分布、性能与生命周期追踪，而不只保存视频。

发布包包含版本化运行时、兼容 EXE/内容清单、配置、明确的不支持版本提示、
成对诊断日志、战役覆盖报告、已知限制及卸载说明。关闭合作加载器后应恢复现有单人流程。
不分发游戏 EXE，不要求永久修改游戏数据或替换系统 DLL。

**最终验收：** 两个远程玩家可以独立驾驶并共同完成约定的全部战役路线，
任务、武器、伤害、结果、重试和存档均一致，所有上线原生适配器都有 ABI、
生命周期、线程和运行证据。达到此前都应标注为研究或原型版本。
